一、系统总览

LeafDepot 是一套基于计算机视觉的烟箱数量自动盘点系统：AMR 机器人载相机逐垛位拍照，算法识别每个储位垛堆的烟箱数量与品规，与系统库存比对生成差异报表。

二、烟箱计数检测算法（core/detection）

算法本质一句话：YOLO 提供"看见了几个框、每个框多宽"，双目 SGBM 深度提供"每个框离相机多远"，pile_ID_*.json 配置把（归一化宽度序列, 深度序列）映射到真实箱数；顶层用该 pattern 匹配计数，下层用垛型模板补齐。

2.1 输入

每个储位 3D 相机产出两张关键图（相机横装，原始 2560×2160）：

文件内容
main.jpg垛堆正面 RGB 图
depth.jpg2×2 四象限立体合成图（左上=左目、右上=右目；不是现成深度图，深度由算法自己算）

另有两路扫码相机图片（scan_camera_1/2/main.jpg），供条码链路使用（见第三章）。

2.2 统一入口与流水线

入口：count_boxes()（core/detection/processors/factory.py:814）→ StackProcessorFactory.count()（factory.py:153）。流水线步骤：

Step 0  图像旋转矫正     main.jpg 逆时针旋转 90°（相机横装矫正）→ 2160×2560 竖图
Step 1  YOLO 目标检测    pile+box.pt, conf=0.65 → 垛堆框(pile) + 烟箱框(box)列表
Step 1.5 深度矩阵生成    depth.jpg 四象限拆分 → SGBM 立体匹配 → 深度矩阵(毫米)
Step 2  场景准备         用 pile 框做 ROI，中心点过滤出属于本垛的箱框
Step 3  分层聚类         按 y 中心一维间隙分裂 → 层列表（自动定层数）
Step 4  层整理           按 avg_y 升序排列（y 小 = 物理上层），index=1..N
Step 5  加载垛型模板     pile_config.json 取该 pile_id 的每层期望箱数
Step 6  计数             满层判断 → 选择处理器 → 顶层 pattern 匹配 + 下层模板 → 总数

输出：一个整数（该储位烟箱总数）。

2.3 Step 0：旋转矫正

_rotate_and_save_image（factory.py:642）：PIL rotate(90) 正角=逆时针，把横装相机原图转成竖图。深度矩阵生成时同样逆时针旋转 90°，保证两套坐标系一致。

2.4 Step 1：YOLO 检测

_run_yolo_detection（factory.py:387）：ultralytics YOLO("shared/models/yolo/pile+box.pt").predict(conf=0.65)。类别定义（pile+box.yaml）：box（烟箱）、pile（整垛）、top（顶层，当前未用）。

2.5 Step 1.5：双目深度计算（SGBM）

DepthCalculator（core/detection/depth/depth_calculator.py），项目自算深度，非相机点云：

  1. 拆图：depth.jpg（2560×2160）按中线切 4 块（每块 1280×1080），取左上=左目、右上=右目；
  2. SGBM 立体匹配求视差 d：window_size=11, num_disp=128, P1=8·3·11², P2=32·3·11², disp12MaxDiff=10, uniquenessRatio=20, speckleWindowSize=200, speckleRange=2；
  3. 三角测量：depth_mm = f·B / d = 6400px × 120mm / d = 768000 / d（焦距 6400px、基线 120mm）；
  4. 视差图逆时针旋转 90°（与 RGB 对齐）→ 深度矩阵存 depth_cache/depth_matrix.csv（行=y 列=x，值=毫米，0=无效）。

工作距离约 9.2m～22m。

2.6 Step 2：场景准备（ROI 过滤）

prepare_logic（core/detection/core/scene_prepare.py:6）：

  1. 取置信度最高的 pile 检测框作为垛堆 ROI；无 pile 框 → 直接返回 0 箱；
  2. 对每个检测框，判断其中心点是否落在 pile 矩形内（不是 IoU）：在 → 保留；不在 → 剔除（背景误检、邻垛箱）。

2.7 Step 3：分层聚类（一维间隙分裂）

cluster_layers_with_box_roi（core/detection/core/layer_clustering.py:122）。不用 KMeans/DBSCAN，层数自动产生：

1. 每个箱取 (yc = (y1+y2)/2,  h = 框高)，按 yc 升序排序（y 小 = 图像上方 = 垛上层）
2. avg_h = 所有箱高度均值
3. 顺序扫描：相邻两箱中心距 gap = yc[i] - yc[i-1]
     gap > threshold → 开新层；否则归入当前层
   自适应阈值（_adaptive_gap_threshold, :11-19）：
     箱总数 < 3 → threshold = 0.8 × avg_h   （箱太少时放宽，避免拆层）
     否则      → threshold = 0.6 × avg_h   （gap_ratio=0.6）
4. 每层输出：index（1=最上层）、avg_y、层 ROI（箱并集上下各外扩 10%·avg_h，裁剪到 pile ROI 内）

物理依据：层间距≈一个烟箱高度，同层箱 y 中心基本对齐；两箱中心 y 距离超过平均箱高的 60% 即认为跨层。

2.8 Step 6a：满层判断（当前策略：恒满层）

CoverageBasedDetector.detect（core/detection/processors/full_layer_detector.py:131）。设计上实现了三个指标（现在只打日志不参与判定）：

  • coverage：顶层箱横向区间并集长度 / pile 宽度（区间排序后做经典区间合并）；
  • cv_gap：箱中心 x 相邻间距的变异系数（std/mean）；
  • cv_width：箱宽变异系数。

同时做一件仍然生效的事：顶层高度过滤——删除高度 < 5%·最大箱高的误检小框，并回写顶层箱列表（后续计数用的是过滤后的箱）。

当前判定逻辑（工作区版本）：无论单层还是多层，一律返回 status="full"——"顶层无论如何都进入深度比对，不在此处做满层判断"。连锁影响：非满层/单层处理器分支当前不可达，所有垛都走满层处理器（见 2.9，及第十一章遗留说明）。

2.9 Step 6b：计数（当前唯一实际路径：TemplateBasedFullProcessor）

process（core/detection/processors/stack_processor.py:202）：

n_detected = 检测到的层数
顶层 = layers[0]（y 最小）
top_count = _calculate_top_layer_count_with_depth(顶层箱, pile_roi, pile_id, 深度矩阵)  ← 见 2.10
若 pattern 反推出的垛型 ≠ 条码给的 pile_id → 用反推垛型重新取模板（条码认错时的兜底）
lower_sum = sum(模板前 n_detected-1 层)     ← 检测 N 层 → 下 N-1 层按模板补齐
total = lower_sum + top_count

计数公式（日志原文）：总箱数 = 顶层深度算法箱数 + 下层模板之和。

例：3×10 垛检测到 3 层、顶层 pattern 命中 10 箱 → total = 10 + 10 + 10 = 30。模板取值方向：第 2 可见层用 template_layers[0]、第 3 可见层用 template_layers[1]……（顶层永远交给 pattern 匹配，模板只补下层）。

2.10 核心子算法：顶层 pattern 匹配

_calculate_top_layer_count_with_depth（stack_processor.py:54-200）：

输入：顶层箱（已按中心 x 从左到右排序）、pile_roi、pile_id、深度矩阵

① 逐箱提取特征：
     norm_width = 箱像素宽 / pile_roi 像素宽          ← 归一化宽度（0~1）
     depth_mm   = 深度矩阵在箱中心归一化坐标处的值
                 （cy_n = cy/图高 + 0.05 纵向标定偏移：深度图与可见光 FOV 垂直不重叠的硬件错位补偿）
                 （采样：5×5 邻域中位数，|值-中位数|≤500mm 过滤离群点，取均值）
② 误检过滤：depth_mm > 21950mm（≈22m）的箱剔除
③ pattern 匹配（按 pile 优先级遍历 pile_ID_*.json 里的每条 pattern）：
     要求：pattern 的 width_ranges / depth_ranges 数组长度 == 顶层箱数
     对第 j 个箱（从左到右）逐一校验：
        width_ranges[j][0] ≤ norm_width_j ≤ width_ranges[j][1]
        depth_ranges[j][0]  ≤ depth_j     ≤ depth_ranges[j][1]
     全部通过 → count = pattern_id 末尾的数字，返回 {count, matched_pile_id}
④ 全不匹配 → 回落 YOLO 计数（= 过滤后的顶层箱数）
为什么"1 个检测框能数出 5 箱"：正面视角下多个烟箱侧面纹理被 YOLO 融合/漏检成一个宽框；一个检测框覆盖的宽度比例（近大远小的透视由深度补偿）对应确定的物理箱数——这正是 pile_ID_*.json 表达的知识。

2.11 深度采样细节

DepthProcessor.extract_depth_at_position（core/detection/depth/depth_processor.py:51）：归一化坐标 → 矩阵像素坐标 → 取 5×5 邻域 → 跳过 ≤0 无效值 → 中位数 ±500mm 一轮过滤 → 剩余 <5 点时 mean±2σ 二轮宽松过滤 → 返回均值（毫米）。

四、检测配置文件详解

4.1 core/config/pile_config.json —— 垛型模板

{"piles": [{"id": 1, "name": "3*10", "layers": [{"index": 1, "count": 10}, ...]}, ...]}
字段含义
id垛型编号（pile_id，1~5）
name垛型名，层数*每层箱数：3*10=3 层×10 箱；4*7+2=4 层×7 箱 + 1 层×2 箱
layers[].count自上而下每层期望箱数（供下层模板补齐）

五种垛型：3*10(30) / 5*8(40) / 5*6(30) / 4*7+2(30) / 5*5(25)。

与储位的映射不是坐标映射，而是条码→垛型：每个储位盘点时扫条码 → 6 位码查表 → 垛型 → pile_id。储位坐标（"排-列-层"）只用于机器人路径排序（见 5.4）。

4.2 core/config/pile_ID_X_*.json —— 顶层 pattern 匹配表

每个文件是 JSON 数组，每条 pattern：

{
  "pattern_id": "double_l_8",
  "visible_count": 2,
  "match": {
    "width_ranges": [[0.4174, 0.5], [0.2852, 0.35]],
    "depth_ranges": [[9200, 11950], [14450, 16950]]
  },
  "result_ids": [0, 7]
}
字段含义
pattern_id命名 {框型组合}_{箱数}：single_l_5=1 个长框→5 箱；double_s_5=2 短框→5 箱；longshort_4=1 长 1 短→4 箱；doubles_long_10=1 长 2 短→10 箱。末尾数字 = 最终计数（代码取 re.findall(r'\d+', pid)[-1]）
visible_count该 pattern 对应的 YOLO 可见检测框数（= width_ranges 数组长度）
width_ranges[j]第 j 个检测框（从左到右）的归一化宽度区间（框像素宽 / pile_roi 像素宽，无量纲 0~1，透视线索：越近越宽）
depth_ranges[j]第 j 个检测框中心点的深度区间（毫米）（双目 SGBM 深度，工作距离 9.2~22m）
result_ids各框对应的储位列号（保留字段，主流程未消费）

后缀约定：_mir = 镜像摆放（左右颠倒的同一种垛型）；_t/_d/_e = 同箱数不同深度位置的变体。各文件规模：ID_1(3x10) 45 条 / ID_2(5x8) 20 条 / ID_3(5x6) 22 条 / ID_4(4*7+2) 31 条 / ID_5(5x5) 17 条。

五、盘点任务编排算法（services）

5.1 任务号生成

_get_next_task_no（services/api/inventory/service.py:105）：格式 HS{YYYYMMDD}{NN}（如 HS2026062801）。持久化计数器 logs/task_no_counter.txt（日期:计数，fcntl.flock 跨进程互斥），日期变更自动归零。另有 RCS 请求号 TASK_ + 12 位十六进制（logs/request_id_counter.txt）。

5.2 任务生命周期

创建（前端勾选仓库/储区/位号 → POST /api/inventory/start-inventory）
  │   全局并发互斥：内存 + task_state.json 双查，running/completed/partial 占用时 409
  ▼
execute_inventory_workflow (service.py:1435) 后台任务
  ├─ 初始化状态 → running → 写 output/task_state.json
  ├─ 预检：RCS TCP 探活 + 三台相机探活（离线 → failed，error_type=rcs|camera，广播弹窗）
  ├─ 寻路排序 sort_bins_by_path（见 5.4）
  ├─ 逐 bin 主循环（每 bin 超时 300s）：
  │    ① 下发单 bin 给 RCS → 登记 rt_code → append 进 submitted_bins
  │    ② wait_for_robot_status("end")  等 AMR 到位回调
  │       超时无 END 且未取消 → 跳过该 bin（不发 continue，见 5.6）
  │    ③ 拍照（gateway 触发三相机脚本，重试 5 轮，只重试失败相机）
  │    ④ 推 Redis 单 bin 队列（触发 worker 检测，不等 continue）
  │    ⑤ 提前下发：先 submit 下一个 bin 存 pending → 给上一个 bin 发 continue 让车走
  │       → 下一轮直接消费 pending 等 END（AMR 移动与检测并行）
  ├─ 等 worker：轮询 worker_completed 集合计数 ≥ len(submitted_bins)
  ├─ 汇总：逐 bin 取回检测结果，与系统库存按 locationName 匹配
  │        bin_result = {actualQuantity, actualSpec, systemQuantity, difference=实际-系统, ...}
  ├─ 终态判定：全成功=completed / 全失败=failed / 混合=partial → 写 task_state.json + WebSocket 广播
  └─ 自动保存 Excel（有效状态=无效，防 gateway 重启丢数据；用户确认后再存"有效"版）

5.3 Redis 队列结构（"3 队列 + 2 集合"）

Key类型方向内容
inventory:single_bin_queueListgateway→worker{task_no, bin_location}，worker BRPOP
inventory:task:results:{task_no}Listworker→gateway检测结果（数量/品规/照片路径），gateway LREM 消费
inventory:pending_queueList已废弃旧批量队列，仅保留兼容
inventory:task:rcs_completed:{task_no}Setgateway 写收到 RCS END 的 bin（进度上半段）
inventory:task:worker_completed:{task_no}Setworker 写检测完成的 bin（进度下半段）

任务结束 DEL 结果表；取消时同时清两个集合并从队列逐条滤出本任务条目（flush_single_bin_queue_by_task）。

5.4 寻路排序算法

sort_bins_by_path（service.py:135）：

  1. bin 名解析为 (row, col, layer)（"排-列-层"）；
  2. 加权距离：|Δrow|×1000 + |Δcol|×10 + |Δlayer|（跨排代价远高于列/层移动）；
  3. 从 row 最小的 bin 起，贪心最近邻逐个选下一个。

5.5 取消机制（秒级退出）

cancel-inventory（inventory/router.py:1056）：

  1. 清 task_state.json；运行中任务只置 cancelled 标志（工作流在多个检查点自然退出）；
  2. 对未收到 END 的 bin 给 RCS 发 continue（让 AMR 离开垛位防锁死）；
  3. 注入假 END 到状态队列唤醒阻塞中的 wait_for_robot_status；
  4. 清 worker 队列中本任务条目 + 两个 Redis 完成集合；
  5. 终态任务取消 → 结果写"无效"Excel + 清内存；WebSocket 广播 task_cancelled。

5.6 超时与提前下发的协作逻辑

  • 提前下发：END 到达 → 拍照 → 推检测 → 先 submit 下一个 bin（存 pending_next_bin）→ 才给当前 bin 发 continue。AMR 在 worker 检测的数十秒里已在去下一垛位的路上；
  • 超时不发 continue：等 END 超 300s 时先倒查队列有无迟到 END；确认没有且未取消 → 直接跳过该 bin，不发 continue（RCS 侧任务节点可能已清理，发了无意义）。

5.7 submitted_bins 机制

工作流内的局部列表，记录"已下发 RCS 且需要收集检测结果的 bin"。三个维护点：正常下发 append、消费提前下发的 pending 时 append（此处曾漏掉导致结果缺行，commit a7907a8 修复）、取消提前退出时 pop 最后一项。用途：worker 完成等待的计数上限 + 最终结果收集的遍历范围。

5.8 recount 重新盘点

前端勾选异常库位 → 生成独立任务号 {taskNo}_R{随机}（独立存储键，不受并发互斥限制）→ 走完整流程 → 完成后只取 recount 集合内的结果覆盖原 inventoryItems → 以 merge:true 把重盘结果按"储位名称"列合并写回原任务号的 Excel。

5.9 进度统计算法

/progress 接口（inventory/router.py:293）：

completed_count = max(rcs_completed 集合数, worker_completed 集合数)
                 （RCS END 到达即计入，worker 完成后覆盖；两者为 0 时回退内存状态计数）
progress = completed / total × 100%

前端 1s 轮询；差异统计中"异常项" = 数量不等 或 品规未识别 或 品规与系统不一致（人工校准过的豁免）。

六、功能模块实现详解

6.1 登录认证

数据流：登录表单（首页即登录页，web/src/components/LoginForm.tsx 挂在 pages/Home.tsx）→ POST /login → 网关把用户名密码以 HTTP 请求头形式（userCode/password）转发 LMS /login → 返回 authToken 存 sessionStorage（刷新不掉线、关浏览器需重登）→ 前端再 GET /auth/token 拉取用户信息。

接口位置逻辑
POST /loginauth/router.py:71-166body 取 username/password → header 转发 LMS；成功写 user_login 操作日志（含 IP/userLevel）；LMS 不可达 503 / 超时 504
GET /auth/tokenauth/router.py:217-236纯代理，按 token 查用户信息，前端登录后/刷新时验证
POST /userManagement/updateUserauth/router.py:169-214改密码/姓名/手机号：非 admin 只能改自己的 userCode+password（白名单过滤字段）；密码走强密码校验（≥8 位，必含大小写/数字/特殊字符）

权限体系：userLevel 分 admin（管理员）/ operator（操作员），存 sessionStorage 供前端 UI 分支。网关没有全局认证中间件（middleware/ 目录为空），需要认证的接口逐个自校验 authToken 头（/lms/getUsers、registerUser、deleteUser、/userManagement/updateUser 等）。

注意：LMS 故障时 get_user_info_from_token() 降级返回 MOCK_USER（admin），用户管理接口的权限检查会放行；管理员专属校验（历史删除、日志清理）依赖前端自报的 X-User-Level 头，可被伪造。详见第十一章。

6.3 历史记录

数据流：历史列表来自 output/history_data/*.xlsx 的索引缓存（内存 dict + 落盘 output/task_index.json）；详情接口重读单个 Excel；图片走 /api/history/image 从 capture_img/ 读文件流。

  • 索引机制（history/router.py）：首次从磁盘加载缓存；GET /api/history/tasks 每次请求增量补充目录中缓存没有的文件（读表头解析"下发时间/操作员/修改记录/有效状态"存 meta）；支持日期过滤，>180 天标记 isExpired；

  • 详情 GET /api/history/task/{task_id}：openpyxl 逐行转 dict（含照片 1~4 路径），汇总 hasModified/isValid；

七、结果回写与报表生成

7.1 update-bins-data 匹配算法（库存回写）

/api/inventory/update-bins-data（inventory/router.py:925-993）：

  1. 读 烟箱信息汇总完整版.xlsx 构建 品名→品规代码 映射表；
  2. 待更新数据按 locationName（储位名称）组织：数量 = actualQuantity、品名 = actualSpec（人工校准值优先）、品规代码 = 查表；
  3. 写回 services/sim/lms/bins_data.xlsx：遍历数据行，按 E 列（储位名称）字符串相等匹配，命中则更新 H 列（数量）、J 列（品规名称）、I 列（品规代码）。

该文件同时是任务创建时的库存数据源 → 本地库存闭环（盘后库存立即生效于下次任务）。

7.2 Excel 报表

output/history_data/{taskNo}.xlsx（shared/excel_writer.py），单 sheet"盘点结果"，16 列：任务编号 / 序号 / 下发时间 / 操作员 / 品规名称(系统) / 储位名称 / 实际品规 / 库存数量(系统) / 实际数量 / 差异 / 修改记录 / 有效状态 / 照片 1~4 路径。

差异列判定顺序：实际品规非空且≠系统品规且≠"未识别" → "品规不一致"；="未识别" → "品规不一致"；否则数量差≠0 → 数字差值；否则 "一致"。

有效状态："有效"= 用户确认保存；"无效"= 自动保存/取消（gateway 重启后 /results 按有效 Excel 恢复）。

八、RCS 机器人交互协议

公共：headers X-App-Id/X-Sign/X-Timestamp/X-LR-REQUEST-ID；失败重试 3 次（退避 (n+1)×2s）；业务失败（success=false）不重试。

动作is_sim=true（本地 sim_rcs_server:4001）is_sim=false（真实 RCS 10.16.82.90:443）

11.2 已知问题与安全注意事项

  1. MOCK_USER 降级放行：LMS 故障时 get_user_info_from_token() 返回 admin 身份，用户管理接口（注册/删除/改密）的权限检查会一律放行（auth/router.py:64-68）。
  2. X-User-Level 头可伪造：历史删除、操作日志删除/清理等 admin 校验依赖前端自报请求头，无服务端验证。
  3. 图片端点无路径穿越防护：两个图片接口的路径参数直接拼接，未做 resolve()/".."检查；/api/inventory/image 的 404 错误会回显服务器绝对路径。
  4. 历史清理参数不匹配：POST /api/history/cleanup 的 days 参数读出未使用、前端传的 cutoff_date 被忽略，"按日期清理"实际退化为"清理 6 个月前"。
  5. 操作日志"清空"未闭环：前端清空按钮不传 logIds，后端因空列表抛 400。
  6. 超时跳过的等待风险：任务主循环超时跳过的 bin 仍留在 submitted_bins 且从未推给 worker，worker 完成计数理论上到不了上限（仅取消能打破等待循环）。

以上第 1~5 项属于安全/功能缺陷，建议排期修复；第 6 项为极端超时场景的边界行为。修复后请同步更新本文档。
